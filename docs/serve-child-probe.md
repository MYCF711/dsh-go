# 探针记录：serve 的子进程（2026-11-03）

## 这轮想验什么

`serve` 起子进程跑 `dshd run`。子进程若在中途被杀，`serve` 会不会留下一个永不结束的 turn
（界面永远停在"正在思考"）。

## 实际发生了什么（与预期不同，如实记录）

```
create            → b497f103-…
prompt1           → accepted turn-1
3 秒后 dshd 进程数 → 1（只有 serve 自己，子进程不存在）
杀掉子进程        → 没找到可杀的（没有 " run " 命令行）
prompt2           → accepted turn-2
```

三个观察：

1. **子进程没有出现在进程表里**——要么它瞬间退出，要么根本没起来
2. `tmp/killchk/logs/dshd-2026-11-03.log` **是空的**（子进程本该写"会话开始"那一行）
3. `prompt2` 被接受（200），说明 busy 已清——turn 确实结束了

## 结论：**这轮没有验到想验的东西**

第 3 点看起来"正常"（崩溃后能继续用），但因为第 1、2 点，
**无法区分**下面两种情况：

- 子进程被杀 → 正常收尾 → busy 清（符合预期）
- 子进程压根没起来 → 立刻失败 → busy 清（机制没被验证过）

这两种在接口上长得一模一样。**不能拿第 3 点当"崩溃处理正确"的证据。**

## 下一轮要做的

1. 先确认 `serve` 到底有没有起子进程：在 `loopRunner.Run` 里记一行日志
   （pid / argv），失败时把 stderr 写进 turn/error（现在只在非零退出时带）
2. 用**真的会跑很久**的任务（例如 `--max-steps 6` + 让它读一个大文件）复现，
   在子进程活着的时候杀它
3. 才谈"崩溃后 busy 会不会卡住"

## 记一笔方法

这一轮我差点写下"崩溃处理已验证"。差一点的理由是第 3 点看起来对——
**"看起来对"正是前面那些假绿（占位符标题、永真 grep、量错对象的门禁）的共同前身。**

---

## 续（第二轮）：加了一行日志才看得见

`loopRunner.Run` 起子进程后往 stderr 写一行：

```
spawn pid=2696 argv=[run --home tmp/spawnchk --session 18ebf4df-… --prompt … --policy deny --max-steps 6]
```

加完立刻能回答上一轮回答不了的问题：**子进程确实起来了**。
上一轮"进程数 1"是因为当时那个任务早已跑完退出，不是没起来。

### 杀掉子进程再试

```
prompt1 → accepted turn-1（子进程 pid=42872 已起）
taskkill /PID 42872         （跑 sleep 30 的中途杀掉）
prompt2 → accepted turn-2
```

第二句被接受 = busy 已清 = 那一轮的 goroutine 真的收尾了。

### 仍然没验到的

**界面那一侧收到的到底是 `turn/error` 还是别的**，这轮没抓 WS。
现在能确定的是「宿主不会卡住」；「界面被告知了什么」还差一次 WS 抓包。

### 方法记一笔

上一轮我写下的结论是「没验到」。这一轮只加了一行 `fmt.Fprintf(os.Stderr, "spawn pid=…")`，
整件事就从"分不清"变成"看得见"。

**排障的第一步永远是让失败可见，而不是猜它为什么失败。**
