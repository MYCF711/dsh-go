> 真正会伤人的是"**有但用不对**"——schema 写歪、描述误导、必填错、后端没配。
> 这些在语料里是**可以算出来的**：每次 `tool/call` 后面都跟着一条结果帧。

80,840+ 次调用，判为失败 1,082（1.3%）

**1.3% 是个健康数字**——说明我们的工具表虽然"紧"（compact 去掉了参数说明），
但并没有紧到让模型频繁填错参数。

## 三条可执行的结论

1. **`web_search` 的 91% 是环境问题，不是代码问题。** 判据：失败信息是
   "宿主没有装搜索后端"。这意味着**任何**在这台机器上用搜索的工作流都会退化——
   它该被体检出来（`dshd doctor` 加一项），而不是等模型调一次失败一次。
2. **`edit` 的 8.7%：拆开看，锅不在"模型写错原文"**。454 条失败样本的错误码分布：

   | 错误码 | 占比 | 意思 |
   |---|---:|---|
   | `FS_STALE_VERSION` | **58.8%** | 读完之后文件被改了 |
   | `FS_NOT_OBSERVED` | **26.7%** | 压根没先读 |
   | `FS_EDIT_NOT_FOUND` | 14.1% | `old_string` 真的不在文件里 |
   | `FS_AMBIGUOUS_EDIT` | 0.2% | 匹配到多处 |

   **85% 是"手上的版本过期了"，不是"记错了原文"。** 所以改措辞没用——要做的是
   把下一步说成一句能照做的话。已落地（`staleEditHint`）：失败时多读一次文件，
   数一下 `old_string` 在新内容里还有几处，然后分别给三种话：

   ```
   仍然唯一 → "再调一次 edit 就会成功（不需要改参数）"
   找不到了 → "先 read 看现在是什么，再决定改成什么"
   有多处   → "有 N 处：给它更多上下文，或传 replace_all=true"
   读不出来 → "先确认这个路径还在"（这时候建议重试才是害人）
   ```

   真机验过两条主路径（见 `modules/tool/edit/stale_hint_test.go`）。
3. **goal 系两个工具 18–25% 的失败里，"这一轮不许改"占大头**——这是**设计使然**，
   但错误文案必须让模型立刻明白"是规则不许，不是我不会"，不然它会反复重试。

## 这份数据怎么用

- 它是一把**回归尺**：改动工具描述/schema 之后，重跑一次看失败率有没有涨。
- 它也是一张**优先级表**：要改工具文案，先看这张表——`update_goal`/`schedule_create`
  比长尾工具值得改。
