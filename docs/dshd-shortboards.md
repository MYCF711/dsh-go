# dshd 自己干活时的真实短板

这份文档只记**实测抓到的**，不记猜测。每次派活之后回来加一条。

它对我们的价值比任何单测都高：单测证明"代码对不对"，这里记的是"**它作为执行者会在哪里掉链子**"。

---

## 1. 「做一个功能」会烧光步数，「写一个文件」才会动手

| 任务书 | 步数 | 工具调用 | 产出 |
|---|---:|---:|---|
| 「在 modules/tool/team/ 加 spawn_teammate，契约如下，参考 team.go」 | 24（用满） | **34** | **0 个文件** |
| 同一件事，但**把接口贴进任务书、禁止读任何已有文件、要求第一步就 write** | 14（上限） | **2** | 202 行，一次通过 |

第二版它在回复里写「你的 24 步里上一次有 34 次工具调用、0 个产出——全是读文件」——
**它读得懂这句话，只是自己不会做这个判断。**

### 可复用的规矩

派活时如果不写死"第一步就是 write"，它会把预算全花在 read/bash 上。
`--max-steps 24` 不是"够它探索"，是"够它把探索走完、然后没时间干活"。

**给它的任务书里，"不许读文件"要单独写成一条铁律，放在最前面。**

## 2. 它自检只查"能不能编译"，不查"落到哪里"

第二次派活它跑的自检是：

```bash
gofmt -l modules/tool/team && go build ./modules/tool/team && echo BUILD-OK
```

BUILD-OK，然后交活。但**文件落到了 `state/mail/agents.json`** 而不是
`state/team/agents.json`——这是接线时的入参错误（我传了信箱目录），
可它做的工具把 `dir` 直接当前缀用，没有留下任何"这里应该是哪个目录"的判断。

**教训（对它）：** 涉及"写到某个目录"时，自检要包含一次**真实路径**的验证，
不是只验编译。（对它也是：我在任务书里写了 `<home>/state/team`，它照做，是我接线错了。）

**教训（对我）：** 验收不能停在"build 过了"。这次是 `find state -name agents.json`
才发现的——**跑一次真机、找到那个文件、看一眼它在哪**，比十个单测有用。

## 3. 坏任务书会让它空转；好任务书它一次就过——第三组对照

| 任务书 | 工具表手册 | 步数 | 调用 | 产出 |
|---|---|---:|---:|---|
| 「参考 team.go，加这个工具」 | 完整 AGENTS.md | 24（用满） | 34 | 0 个文件 |
| 接口贴进书里 + 禁止读文件 + 第一步 write | 完整 AGENTS.md | 14 | **2** | 202 行 |
| **写四个测试**，接口/构造方式/断言要点全贴 | 完整 AGENTS.md | 12 | **9** | 4 个测试，全绿 |

第三组（写测试）是 9 次调用——比之前好，但仍然比"写实现"那次的 2 次多。
差别在于：测试需要知道真实行为，而书上没有把"守卫怎么写的"告诉它，
它只能自己读实现（读文件是允许的，上限 2 个）。

**结论：信息给够了它就快；给不够它就去读，而"读"是最贵的。**

### 变异测试：确认它写的测试不是废的

四个测试全绿**不等于**有用。我把实现临时改坏两次：

| 变异 | 结果 |
|---|---|
| 去掉"别人认领不许删"的守卫 | `--- FAIL: TestDeleteRefusesOtherOwnersTask` |
| 去掉归档调用 | `--- FAIL: TestDeleteArchivesTask` |

每个变异都被**对应的**那个测试抓住，没有"全都红"也没有"全都不动"。
**以后验收它写的测试，一律这么做一遍**——全绿只说明它写得出能跑的测试。

## 4. 它会把"我编的"当成"你要求的"

同一个任务两次，它给 `spawn_teammate` 写的 `Description` 是
「在团队名单里登记一个具名队友，之后可以反复给它派任务而不用重述背景。」（34 字）。

这没问题。但它在真机里对用户说的第一句话是
「我在**她**的初始提示里已经把职责写清楚」——用了"她"，而 prompt 里没有性别。

小事，但说明它在补充细节时**不会标记哪些是补充的**。凡是需要"只做契约要求的事"的场合，
契约要写得足够机械（六道校验逐条列编号那种），别留解释空间。

---

## 5. 它写的**验收工具本身**也会有假阳性

派它写 `scripts/mutate.py`（把实现改坏、看对应测试会不会红）。第一版跑起来很漂亮：

```
breaks-compile                   CAUGHT         0.5s
全部被测试抓住
```

但那条变异是**把代码改成编译不过**。包根本没编译，测试一行都没跑——
它把"编译失败"当成了"测试抓住了变异"。

**后果比 bug 更糟**：这个工具的全部意义就是抓"测试是废的"，
结果它能被任何坏变异骗过——**验收工具自己有假阳性，等于没有验收**。

返工只改了一处：判 `CAUGHT` 之前先扫 `go test` 输出里有没有
`[build failed]` / `undefined:` / `cannot use ` / `syntax error`，
有就报 `BAD`。

### 规矩

**给"验收工具"写验收用例时，第一条必须是"它能不能识别出坏的输入"。**

我验证它的三个用例：
| 输入 | 期望 | 实际 |
|---|---|---|
| 正常的变异（真会被测出） | CAUGHT | CAUGHT，退出码 0 |
| 不影响断言的变异 | MISSED，退出码 1 | MISSED，退出码 1 |
| 编译不过的变异 | BAD，退出码 1 | BAD，退出码 1，还带出了报错行 |

外加一条：**每次跑完 `git status` 必须是空的**——它临时改的是真源码，
恢复不可靠就等于毁掉正在做的工作。

## 6. 一个"度量"坑：管道会掩盖退出码

第一次验 `mutate.py` 的退出码，我写的是：

```bash
python scripts/mutate.py | tail -6
echo "退出码=$?"        # ← 这是 tail 的退出码，不是 python 的
```

于是它报了 `MISSED`、脚本自己也说要退出 1，我却看到 `退出码=0`，
差点当成脚本的 bug 去改。

**判退出码的检查，永远不要经过管道**。要么直接跑，要么用 `${PIPESTATUS[0]}`。

## 自验：从"不跑"到"会跑"，只差一句放在第一行的话（2026-11-03）

### 过去的观察（写在这里的旧短板）

> 它写完不跑：交代码、不执行、也不贴输出。

### 今天的实验

同一个任务（写一个小脚本数 `/api` 方法个数并与期望值比对），两次派活只差一处：

| | 自检要求的位置 | 它做了什么 |
|---|---|---|
| 之前 | 文末「要求」第 5 条 | 写完即止 |
| 今天 | **第一行，且写明"没贴输出 = 没完成"** | **跑了、贴了输出、还指出一个假绿风险** |

它的原话：

```
共 13 个（期望 13）
退出码=0
……我还顺便在内存里验证了两条失败分支（没有直接动文件）
```

以及一句我没要求它说的话：

> 把 `config.set` 改名来模拟"少一个"时计数仍然是 13，因为改名不会减少常量声明的数量——
> 如果有人想用改名测这条门禁，会得到一次假绿灯。

**这条观察是对的**，而且是它自己发现的。

### 怎么解释这件事

不是它"愿不愿意"的问题，是**任务书有没有把"跑"算成交付的一部分**。

之前我把自检当成"建议"（写在要求列表里），它就把交付理解成"写出文件"。
今天我把自检写成**完成的定义**（第一行、否则当没交），它就照做了。

### 但它仍然不会主动做的一件事

**它不会自己想到要验失败分支**——今天那次是它顺手做的，不是任务书要求的。
所以派活时仍然要写清"改坏一个值 → 应该红"这种可执行的自检步骤。

### 结论（已写进派活模板）

`docs/WORKER.md` 第一行现在是那句话。**位置不是排版问题，是行为问题。**

### 第三次复现（2026-11-03，写 `scripts/doc-links.py`）

新模板下再派一次，这次任务更难（要读 AGENTS.md、还要**造一个失败分支**再还原）：

- ✅ 跑了主路径，贴了输出
- ✅ **造了失败分支**（改 AGENTS.md 造伪引用 → 脚本报 MISS → `git checkout` 还原），也贴了输出
- ✅ 交付物完整可用（1,395 字节），第一次跑就抓到真问题：`AGENTS.md` 引用了不存在的 `docs/cordis-alignment.md`

三次派活，唯一变量是任务书第一行：

| 轮 | 任务 | 自验 |
|---|---|---|
| 137 | `full-e2e.py` | ❌ 没跑 |
| 138 | `api-methods.py`（模板改第一行） | ✅ 跑了 + 指出假绿风险 |
| 140 | `doc-links.py`（新模板 + 造失败分支） | ✅ 跑了 + 造了失败分支 + 贴了输出 |

**结论升级**：不是「两次观察」，是**三次一致**。
模型的能力边界不是常量——**它取决于任务书把什么写成"完成"的定义。**

## 它能自己跑门禁并正确判断（2026-11-03）

派活：`用 bash 跑 bash scripts/check.sh，只回答三件事：最后一行、PASS/FAIL 行数、能不能提交。不要做任何修改。`

它的回答：

```
① 最后一行：ALL GREEN（脚本退出码 0）
② PASS 27 行，FAIL 0 行（另有 1 行 SKIP：-race 不可用……走 race-guard 结构性补偿）
③ 能提交。
```

**我独立核对**：

```
退出码=0
PASS 行数: 27
FAIL 行数: 0
SKIP 行数: 1
```

**三个数全部对得上**，而且它引用了 `docs/ci-rules.md` 里"代理项"的说法来解释那个 SKIP——
不是把 SKIP 当没看见，也不是当成失败，而是**按本仓既有约定判断它不阻断**。

### 这意味着什么

「自己开发自己」最关键的一环不是"能写代码"，是**能判断自己写的对不对**。
今天这条验过了：它跑一次门禁、数对了行、给出了与事实一致的结论。

### 边界

- 它只跑了 1 次、1 条命令，**没做跨多次的稳定性判断**
- 它没被要求处理"红的情况"，所以**还不能说它会诊断失败**

---

## 它能诊断一个真实的红 —— 但步数不够时会一直查下去（2026-11-03）

做法：把 `defaultRunPolicy` 从 `auto` 改成 `allow`，门禁立刻红两条：

```
FAIL  权限分支守卫: 新的权限分支没登记：cmd/dshd/main.go::cmdTools
FAIL  run --policy 默认值可疑（必须是 auto/ask：默认 allow = 静默放行写操作）
```

然后派它读门禁输出并诊断（**明确说不要动手改**）。

### 第一次（6 步）：没答上

它跑去读 `perm-guard.py`、`perm-gates.json`、`grep` 源码，**用满 6 步仍在查，一个字没答**。

### 第二次（12 步）：答对了

它给的结论：

- 抄出了那两条 FAIL 的原文
- 判断**要改回 `cmd/dshd/main.go` 的默认值**，而不是去改 `check.sh` / `perm-gates.json` / `perm-guard.py`
- 并指出「第一条是跟着那个 `"allow"` 字面量走的，改回去两条一起消失」
- **没有动手改**

这个判断是对的：门禁在报"默认值可疑"，正确的修法是改回默认值，
而不是把守卫登记成合法（那是**把报警器关掉**）。

### 边界（重要）

- **6 步不够**：它会在"查证"里耗尽，宁可继续读文件也不给结论
- **给 12 步就收敛**：说明不是不会诊断，是需要给它读够几个文件的预算
- 它没有把"改动守卫清单"当成解法——这一条尤其关键，因为那是最省事也最危险的"修法"

### 记一笔

诊断类任务的步数预算要比写代码任务**更高**，不是更低。
写代码只要 1 次 write，诊断要看门禁输出 + 守卫脚本 + 源码三处。

## 压力测试：让它自己找目标 —— 失败（2026-11-03）

派活：*"check.sh 里有些检查从没被证明过会红。你自己找出一项，证明它会红，写一份报告到 `docs/gate-gap.md`。"*

给到 **18 步**，四条模板规矩全在。

### 结果：28 次工具调用，0 产出

- `docs/gate-gap.md` 不存在
- 工作区干净（**它至少还原了所有临时改动**——这算守住了第三条）
- 轨迹显示它在 `acp.go`、`grep remember`、`go run` 之间来回换方向

### 这说明什么

**四条规矩管的是"怎么做"，不管"做哪个"。**

| 任务形态 | 结果 |
|---|---|
| 目标写死（写这个文件 / 改这个文件 / 诊断这个红） | ✅ 三次复现都成 |
| **目标要自己找**（"从十几项里挑一项"） | ❌ 28 次调用 0 产出 |

它不是在偷懒，是在**搜索空间里迷路**：每一项都要读脚本、想怎么改坏、改坏、跑、还原——
成本差不多，没有依据判断"该挑哪个"，于是一直在比较。

### 下次怎么派

**把选择收窄到 2–3 个候选，但保留"哪一个"的判断权**：

> "这三项里，只有一项是真守卫：A / B / C。你选一个验，写报告说明为什么选它。"

这样既保留了判断，又把无限搜索变成有限比较。

### 记一笔

**"给目标"和"给方向"是两种任务。** 前者它已经稳定；后者还没有验证过能成。
把它当前能力写成"能做任何任务"是过度宣称——**今天这一轮就是反例。**

### 收窄到三个候选：仍然失败，而且**这次它没还原**（2026-11-03）

按上一轮的推论，把候选从"十几项"收窄到 3 个（A 工具表默认 compact / B acp 不默认记住授权 / C 二进制体积），
其余不变，18 步。

结果：

- 21 次工具调用，**仍然 0 产出**（`docs/gate-gap.md` 不存在）
- 更要紧的：**它 `sed -i` 改坏了 `cmd/dshd/main.go` 的 `defaultToolSchema`，然后没有还原**
- `git status` 显示 ` M cmd/dshd/main.go`，门禁是红的（我验的时候）

### 这比"没产出"严重一个量级

上一轮它至少还原干净了。这一轮**它把仓库留在坏状态**——
而任务书第三句明写"结束时 git status 只能有这一个新文件"。

不是不知道规则，是**规则和"继续探索"冲突时，它选了探索**。

### 我的处置

`git checkout -- cmd/dshd/main.go` 还原，门禁回到 ALL GREEN。没有让它重试。

### 结论修正

上一轮我写"把选择收窄到 2–3 个候选"是**基于一个未经验证的推断**做的建议。
实测：收窄不管用。**失败原因不在候选数量。**

真正缺的是：这类任务要求"改坏→跑→还原→写报告"四步闭环，
而它在**中途被打断（步数用尽）时没有"收尾"的自觉**——
写代码任务不会遇到这个，因为交付物就是最后一步。

### 这条要进模板（第四条之外）

> **会产生副作用的任务，必须在任务书里给出"中断时的收尾要求"**：
> "如果步数快用尽，优先还原，不要优先继续探索。"

现在的模板三条规矩都假设"它能跑到最后一步"。**步数上限打破了那个假设。**
