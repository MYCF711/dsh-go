# dshd 自己干活时的真实短板

这份文档只记**实测抓到的**，不记猜测。每次派活之后回来加一条。

它对我们的价值比任何单测都高：单测证明"代码对不对"，这里记的是"**它作为执行者会在哪里掉链子**"。

---

## 1. 「做一个功能」会烧光步数，「写一个文件」才会动手

| 任务书 | 步数 | 工具调用 | 产出 |
|---|---:|---:|---|
| 「在 modules/tool/team/ 加 spawn_teammate，契约如下，参考 team.go」 | 24（用满） | **34** | **0 个文件** |
| 同一件事，但**把接口贴进任务书、禁止读任何已有文件、要求第一步就 write** | 14（上限） | **2** | 202 行，一次通过 |

第二版它在回复里写「你的 24 步里上一次有 34 次工具调用、0 个产出——全是读文件」——
**它读得懂这句话，只是自己不会做这个判断。**

### 可复用的规矩

派活时如果不写死"第一步就是 write"，它会把预算全花在 read/bash 上。
`--max-steps 24` 不是"够它探索"，是"够它把探索走完、然后没时间干活"。

**给它的任务书里，"不许读文件"要单独写成一条铁律，放在最前面。**

---

## 2. 它自检只查"能不能编译"，不查"落到哪里"

第二次派活它跑的自检是：

```bash
gofmt -l modules/tool/team && go build ./modules/tool/team && echo BUILD-OK
```

BUILD-OK，然后交活。但**文件落到了 `state/mail/agents.json`** 而不是
`state/team/agents.json`——这是接线时的入参错误（我传了信箱目录），
可它做的工具把 `dir` 直接当前缀用，没有留下任何"这里应该是哪个目录"的判断。

**教训（对它）：** 涉及"写到某个目录"时，自检要包含一次**真实路径**的验证，
不是只验编译。（对它也是：我在任务书里写了 `<home>/state/team`，它照做，是我接线错了。）

**教训（对我）：** 验收不能停在"build 过了"。这次是 `find state -name agents.json`
才发现的——**跑一次真机、找到那个文件、看一眼它在哪**，比十个单测有用。

---

## 3. 坏任务书会让它空转；好任务书它一次就过——第三组对照

| 任务书 | 工具表手册 | 步数 | 调用 | 产出 |
|---|---|---:|---:|---|
| 「参考 team.go，加这个工具」 | 完整 AGENTS.md | 24（用满） | 34 | 0 个文件 |
| 接口贴进书里 + 禁止读文件 + 第一步 write | 完整 AGENTS.md | 14 | **2** | 202 行 |
| **写四个测试**，接口/构造方式/断言要点全贴 | 完整 AGENTS.md | 12 | **9** | 4 个测试，全绿 |

第三组（写测试）是 9 次调用——比之前好，但仍然比"写实现"那次的 2 次多。
差别在于：测试需要知道真实行为，而书上没有把"守卫怎么写的"告诉它，
它只能自己读实现（读文件是允许的，上限 2 个）。

**结论：信息给够了它就快；给不够它就去读，而"读"是最贵的。**

### 变异测试：确认它写的测试不是废的

四个测试全绿**不等于**有用。我把实现临时改坏两次：

| 变异 | 结果 |
|---|---|
| 去掉"别人认领不许删"的守卫 | `--- FAIL: TestDeleteRefusesOtherOwnersTask` |
| 去掉归档调用 | `--- FAIL: TestDeleteArchivesTask` |

每个变异都被**对应的**那个测试抓住，没有"全都红"也没有"全都不动"。
**以后验收它写的测试，一律这么做一遍**——全绿只说明它写得出能跑的测试。

## 4. 它会把"我编的"当成"你要求的"

同一个任务两次，它给 `spawn_teammate` 写的 `Description` 是
「在团队名单里登记一个具名队友，之后可以反复给它派任务而不用重述背景。」（34 字）。

这没问题。但它在真机里对用户说的第一句话是
「我在**她**的初始提示里已经把职责写清楚」——用了"她"，而 prompt 里没有性别。

小事，但说明它在补充细节时**不会标记哪些是补充的**。凡是需要"只做契约要求的事"的场合，
契约要写得足够机械（六道校验逐条列编号那种），别留解释空间。

---

## 5. 它写的**验收工具本身**也会有假阳性

派它写 `scripts/mutate.py`（把实现改坏、看对应测试会不会红）。第一版跑起来很漂亮：

```
breaks-compile                   CAUGHT         0.5s
全部被测试抓住
```

但那条变异是**把代码改成编译不过**。包根本没编译，测试一行都没跑——
它把"编译失败"当成了"测试抓住了变异"。

**后果比 bug 更糟**：这个工具的全部意义就是抓"测试是废的"，
结果它能被任何坏变异骗过——**验收工具自己有假阳性，等于没有验收**。

返工只改了一处：判 `CAUGHT` 之前先扫 `go test` 输出里有没有
`[build failed]` / `undefined:` / `cannot use ` / `syntax error`，
有就报 `BAD`。

### 规矩

**给"验收工具"写验收用例时，第一条必须是"它能不能识别出坏的输入"。**

我验证它的三个用例：
| 输入 | 期望 | 实际 |
|---|---|---|
| 正常的变异（真会被测出） | CAUGHT | CAUGHT，退出码 0 |
| 不影响断言的变异 | MISSED，退出码 1 | MISSED，退出码 1 |
| 编译不过的变异 | BAD，退出码 1 | BAD，退出码 1，还带出了报错行 |

外加一条：**每次跑完 `git status` 必须是空的**——它临时改的是真源码，
恢复不可靠就等于毁掉正在做的工作。

## 6. 一个"度量"坑：管道会掩盖退出码

第一次验 `mutate.py` 的退出码，我写的是：

```bash
python scripts/mutate.py | tail -6
echo "退出码=$?"        # ← 这是 tail 的退出码，不是 python 的
```

于是它报了 `MISSED`、脚本自己也说要退出 1，我却看到 `退出码=0`，
差点当成脚本的 bug 去改。

**判退出码的检查，永远不要经过管道**。要么直接跑，要么用 `${PIPESTATUS[0]}`。
