# `subagent_fork` 该不该做：先把"量"做对

语料里 `subagent_fork` 出现 **112 次**，是工具面上最后一个有名有姓的缺口。
但在决定做它之前，先要回答一个问题：**异步到底省了什么？**

这一轮量了两次，第一次的结论是错的。两次都记在这里。

---

## 第一次量：结论错在"用什么当观察窗"

我数的是"`subagent_fork` 之后、父代理下一次说人话之前，还有多少次工具调用"：

```
样本 112
中位 142 次调用（均值 156，最大 365）
立刻等结果的：0    先干别的：112
```

看上去是铁证：**每一个 fork 都是"派出去就接着干"，没有一个在等。**
按这个结论就该马上做异步版。

**但这个观察窗是错的。** 它数的是"父代理多久之后开口说一段话"，
而模型在长任务里本来就很少开口——中间夹着几十上百次工具调用是常态。
这些调用发生在父代理**已经拿到结果之后**，跟异步没关系。

## 第二次量：直接看"调用 → 它自己的结果"之间隔了几个事件

```
subagent        样本  78   调用→结果之间的事件数：中位 +1   最大 4
subagent_fork   样本 112   调用→结果之间的事件数：中位 +2   最大 3
```

两种模式在**事件顺序上几乎没有区别**：结果都在一两步之内就回来了。

## 真正诚实的结论

**这个指标测不出异步的好处。**

事件是按"谁先被消费"排的，不是按墙上时间排的。同步与异步的差别在于
"父代理在这段时间里**能不能**发起别的工具调用"，那是**墙上时间**的事，
从事件序列里根本看不出来——两边的序列可以一模一样。

也就是说：我手上有的语料，**没有**回答"异步省了什么"的能力。
要回答它，得量墙上时间：同一个任务，同步要多久、异步要多久、中间能不能插活。

## 决定：现在不做

三条理由，按份量排：

1. **没有测量支撑**。上面第一次的"证据"已经被第二次推翻，剩下的只有"上游有、我们没有"这个弱理由。
2. **架构上确实缺通道**（这是早就写在 AGENTS.md 里的）：ACP 侧没有"宿主主动把结果推给客户端"
   的路子，同步实现不是为了省事，是因为异步要的通道不存在。
3. **工具表已经在预算边上**：42 个 / 默认压缩表 4,149 token（P0 目标 ≤6k）。
   为一个测不出收益的能力再加一个工具，是最差的花钱方式。

## 什么情况下重新打开

写清楚触发条件，免得下次又从头吵一遍：

- 出现**真实的等待代价**：有一轮任务里，子代理要跑几十秒而父代理本来可以接着干别的活。
  这类会话能从 `<home>/logs/` 里按工具耗时直接挑出来（`bash`/`subagent` 的 ms 字段）。
- 或者 ACP 上游加了宿主主动推送的通道——那时异步不再需要自造轮子。

## 记一笔方法论

**同一个问题，换一个"什么算证据"就会换一个结论。**

第一次我数"父代理多久开口"，得到一个漂亮的 112/112；第二次数"结果多久回到事件流"，
发现两种模式没区别。两次都很像"数据说话"。

区别在于：第一个指标**看起来**在回答"有没有在等"，其实在回答"模型说话密不密"。

**指标选错的时候，它不会报错——它会给你一个更干净的数字。**

## 重新评估（2026-11-03，第 78 轮）

### 新证据一：`subagent_fork` 的参数和 `subagent` 一模一样

从真实语料里抠出三条调用样本，参数都是：

```json
{"description": "Dissect official Electron shell", "prompt": "任务：解剖官方 DSH 桌面壳…"}
```

也就是说**没有** "异步"、"回调"、"parent_id" 之类的字段。
当初把它归类成「`subagent` 的异步变体」，方向就错了——
两者的差别不在时间上，而在**子代理看不看得到父会话的上下文**。

### 新证据二：我们自己的 `subagent` 是"全新"的

`cmd/dshd/subagent.go` 的 `RunSub` 里没有任何历史注入：它拿 `req.Prompt` 起一个新会话。
所以 `subagent_fork` 缺的不是异步，而是**继承父会话 surface 再跑**。

### 新证据三：当初三条不做的理由，有两条已经不成立

| 当初的理由 | 现在 |
|---|---|
| 没有测量支撑"异步省了什么" | 仍然成立，但**这个问题已经不相关**了（差别不在异步） |
| ACP 没有宿主推结果的通道 | `serve` 已经有 WS 推送，这条理由弱化 |
| 工具表在预算边上 | 实测真实成本 **23172 字节**（compact），离 32 KB 有余量 |

### 结论（改判）

`subagent_fork` **值得做**，但做的方式和最初设想不同：

- 不做异步回调——语料里没有任何证据表明模型需要它
- 做的是「**继承父会话历史后跑一个子轮**」：复用现有 `spi.SubagentProvider`，
  在 `RunSub` 之前把父会话最近 N 条消息塞进子循环

### 下一步（可派活的形状）

1. 给 `spi.SubagentRequest` 加 `InheritSession string`（空 = 不继承，行为不变）
2. `RunSub` 在它非空时，先从 `session.Source` 读父会话最近 N 条，作为子循环的初始历史
3. 新模块 `modules/tool/subagentfork`：`Name()` 返回 `subagent_fork`，其余复用
4. 验收：真机让子代理回答一个**只有父会话里才有的暗号**

### 记一笔方法

这份文档第一版把 `subagent_fork` 判成"异步变体"，依据是"名字里有 fork"。
一条参数样本就能推翻它——**而我当时一次也没去看参数长什么样**。

名字是最不可靠的证据。
