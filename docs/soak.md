# 长期运行（soak）：跑很多轮之后，会不会涨

`python scripts/soak.py --turns 120`

不是测"能不能跑"——那是 e2e 的事。这里盯的是**时间的形状**：RSS、句柄、每轮耗时、磁盘。

## 形状：前 30 轮爬升，之后平

**120 轮纯聊天**（一个进程连吃）：

| 轮次 | RSS | 句柄 |
|---|---:|---:|
| t001–t015 | 16,841 KB | 158 |
| t016–t030 | 19,045 KB | 177 |
| t031–t045 | 19,536 KB | 182 |
| t046–t060 | 19,554 KB | 188 |
| t061–t075 | 19,580 KB | 188 |
| t076–t090 | 19,973 KB | 191 |
| t091–t105 | 19,823 KB | 196 |
| t106–t120 | 20,157 KB | 196 |

**40 轮带工具**（每轮真调 `read`）形状一样：

```
t001-005: 16,572KB / 161      t021-025: 19,627KB / 188
t006-010: 18,530KB / 184      t026-030: 19,772KB / 188
t011-015: 19,186KB / 186      t031-035: 19,777KB / 188
t016-020: 19,086KB / 186      t036-040: 20,060KB / 194
```

**判定：趋稳，不是线性泄漏。**

依据不是"涨幅百分比小"，而是**曲线形状**：t030 之后连续 45 轮句柄停在 188–196、
RSS 停在 19.5–20.2 MB。线性泄漏不会这样——它会一直往上走。

前 30 轮的爬升是 Go 堆目标 + 连接池预热，不是持有不还。

## 每轮耗时没有变慢

120 轮里每轮往返都是 1s 上下（模型是本地网关，纯聊天）。带工具的 40 轮是 1–2s
（多一次工具往返）。**第 120 轮不比第 1 轮慢。**

## 磁盘：线性增长，但那是设计

120 轮之后 home 是 75 KB，约 **600 字节/轮**。这是 append-only 的会话日志本身——
**日志永不删**（红线 R5）。要省空间靠压缩（`compaction/summary` 遮蔽），
不是靠截断。这条不是问题，是承诺。

## 过程中踩的一个坑：客户端必须应答 `session/request_permission`

第一次跑 soak 时，第一轮卡了 119 秒没返回。查下来**不是产品慢**：

服务端在处理会改世界的工具时，会反向给客户端发一个请求：

```json
{"jsonrpc":"2.0","id":"srv-1","method":"session/request_permission",
 "params":{"sessionId":"…","toolCall":{"title":"…"},"options":[…]}}
```

我的测试客户端只读不答，服务端就一直等 —— 整轮永远不返回。

修法：看到带 `id` 的 `method` 消息就是**服务端发来的请求**，必须回：

```json
{"jsonrpc":"2.0","id":"srv-1",
 "result":{"outcome":{"outcome":"selected","optionId":"allow-once"}}}
```

> 这条对所有自己写 ACP 客户端的人都是坑：**只监听 response 不看 request，就会挂死。**
> 而且挂死时没有任何报错——看起来像"模型不响应"。

## 没做的事

- 120 轮不是"跑一整夜"。一整夜是 ~86400 秒 ÷ 1 秒/轮 ≈ 8.6 万轮，
  本次只跑了 120 轮。形状收敛的证据在，但"8 万轮之后仍然平"是**外推**，不是实测。
- 多进程版（`--agents N`）只跑了小样本，没有单独出曲线。
