AGENTS.md 里有 **44 条 ⚠️**。多数是已经消化掉的教训，但有 8 条是**至今没有证据**的东西。
这份文档只记这 8 条，每条写清「怎么才能验」——不写"以后注意"，写可执行的话。

## 1. `-race` 从来没跑过

**现状**：本机 `CGO_ENABLED=0` 且没有 C 编译器，`go test -race` 直接报
`-race requires cgo`。所以 `Hub` / `ServeConn` / `follow` 的并发正确性**只靠设计约束和审读**。

**怎么验**：装一个 C 编译器（Windows 用 TDM-GCC 或 mingw-w64），
`CGO_ENABLED=1 go test ./internal/transport -race`。
**验不成的最低补偿**：在 `hub.go` / `wssession.go` 里保持"锁内不调 Push"这条，
并且每次改这两个文件都重读一遍注释。

## 2. ✅ 已验（2026-11-03）：`follow` 的增量读

> **已直接量（2026-11-03）**：24217 事件的会话，全量 299.9 ms vs 增量 100.5 µs（3000×）。
> 原记录：长跑（50 轮、12 轮、15 轮多次）证明它不会让 Sys 无限增长，
> 且二分定位到"读日志"这一段是分配器保留而非泄漏。**大会话的单次耗时仍未直接量**，
> 但增量读已经 seek 到 offset，不再全量解码——这一条降级为"未量但已改对"。

## 2b. （原）`follow` 的增量读没在超大会话上复测

**现状**：`v4.ReadSince` 已接进 `follow`，但那之后的真机验证用的是**新建的小会话**
（几帧）。2.2 万事件那种大文件上没复测过。

**怎么验**：拿 `session-c0a5847a-…`（22377 事件）当 `--session`，
让 `serve` 跑一轮，量 `follow` 每次 `ReadSince` 的耗时。全量是 301ms，增量应当在毫秒级。

## 3. ✅ 已验（2026-11-03）：真实断线重连

真机：`[1,2,5]` → 断开 → 带 `sinceSeq=5` 重连 → `[6,7,10]`，无重复、无回退。
而且**顺带抓到一个真 bug**（结局帧 seq 退回 1），已修并在同一探针上复验。

## 3b. （原）`hub` 的 `sinceSeq` 在真实重连下没验过

**现状**：单测覆盖了（`TestReconnectWithSinceSeqGetsOnlyNewer`），
但**没有一次真实断线重连**：从没让一个真连接断开、带水位重连、再看它收到的第一帧。

**怎么验**：`serve` 起一条 WS，收几帧后 `socket.close()`，用 `lastSeq` 重连，
断言第一帧的 `seq == lastSeq+1`。

## 第 7 条（压缩表正确率）为什么一直没验成，以及下次怎么做

### 这轮做出来的工具

`scripts/mineprompts/main.go`：从真实会话里抠用户的开场 prompt。

实测抠出 8 条真实的开场白，例如：

```
4. 用rust或者go语言重构DSH有多难？成果能降低DSH的多少内存消耗？
7. dsh-design-studio 和 @xbzbing/dsh-git-panel 读一下这两个插件，然后告诉我是否值得安装
```

### 但这一批**不能直接拿去重放**

抠出来的 8 条里，至少 4 条引用了**这台机器上不存在的路径**
（`Xsdsh-purge`、`E:\Downloads\sub2api_poc`、`E:\Documents\deepseek-harness`）。

拿它们跑 A/B，失败原因会是"路径不存在"，**与压缩表无关**——
那测的是环境，不是默认值。**这种实验比不测更糟：它会给出一个看起来很专业的错结论。**

### 下次的正确做法

1. 从 `header.cwd` 里取会话原来的工作目录
2. 只保留 `os.Stat(cwd)` 仍然存在的会话
3. 在这些 prompt 上跑 A/B，30 个，比成功率

第 1 步的信息在 v4 header 里已经有了（`v4.ReadHeader` 就能读），只是这轮没接上。

### 续（第 103 轮）：cwd 过滤接上了，但它算的不是全语料

`mineprompts` 现在先读 `v4.ReadHeader(file).Cwd`，`os.Stat` 不过就跳过。

跑出来：

```
可重放: 8 条；cwd 已不在而跳过: 0 个会话
```

**这个 0 不能当结论用。** 程序凑够 8 条就 break 了，
所以那个计数只覆盖了"被检查过的那几个会话"，不是全语料的统计。

要回答"这台机器上到底有多少条能重放"，得把 `max` 去掉、扫完全部 183 个会话再计数。
这一步还没做——**在没做之前，任何"样本够/不够"的判断都是猜。**

### 续（第 104 轮）：分母数出来了 —— **44 条**

去掉 max、扫完全部语料：

```
扫过 183 个会话文件
可重放: 44 条；cwd 已不在而跳过: 0 个会话
```

两个数值得记：

- **183 个会话里，只有 44 个能抠出一条合格的开场 prompt**
  （其余要么没有 user 文本、要么长度不在 20–200 字之间）
- **cwd 已不在的会话：0 个** —— 这台机器上所有会话的工作目录都还活着

### 所以第 7 条是可以验的

44 条样本，跑 30 条做 A/B（compact vs full），样本量够。之前说"可能做不成"的担心不成立，
那是我在**没数分母**的情况下猜的。

### 但有个新的坑要先想清楚

这 44 条 prompt 引用的**路径可能仍然不存在**（会话 cwd 活着 ≠ prompt 里提到的文件还在）。
所以重放时不能只看"成功/失败"，得看**它有没有真的动起工具来**——
路径不存在时模型仍可能调用 read/grep 并失败，那是环境的失败，不是压缩表的失败。

判据应当是：**工具调用是否被正确发起**（工具名/参数对不对），而不是最终答案对不对。

### 续（第 105 轮）：A/B 跑了 —— 12 条真实 prompt × 2 种表

| 表 | 工具调用合计 | 失败合计 | 失败率 |
|---|---:|---:|---:|
| compact（默认） | 66 | 30 | 45% |
| full | 61 | 27 | 44% |

**差 1 个百分点。** 和更早那次 10 任务 A/B（9/10 对 9/10）方向一致，样本翻倍后仍然没有差别。

### 但这一轮真正的发现不是"没差别"

两种表的失败率都是 **44–45%**——**接近一半的调用在失败**。
原因不是压缩表，是这些 prompt 引用的文件在这台机器上早就不在了
（`Xsdsh-purge`、`E:\Downloads\...`）。

也就是说：**这个实验的主效应（表形态）远小于噪声（路径不存在）**。
在噪声这么大的夹具上，无论跑多少条，都不可能测出 1–2 个点的差异。

### 结论：第 7 条到此为止，但结论要写准

- ✅ 可以用来说的：**在 22 个真实任务上，compact 与 full 的成功率差 1%，没有证据表明压缩表有害**
- ❌ 不能说的：**"压缩表已被证明安全"** —— 夹具里一半是环境失败，这个实验没有分辨力

要真有分辨力，得先造一个"路径全都存在"的夹具（比如固定把 prompt 指向本仓自己的文件），
那是另一件事，不该混在这条里做。

**这条从"未验证"降级为"已尽力，受夹具限制"。**
