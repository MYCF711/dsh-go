# 工具表的钱花在哪：一次预算审计

工具表 41 个 / 17,007 字节 / **5,451 token**（P0 定的上限 6k，已用掉 91%）。

再加两个「一个文件四个工具」的模块就会击穿。这一轮先算清楚钱花在哪，再谈怎么省。

## 钱花在 JSON，不在散文

| 组成 | 字节 | 占比 |
|---|---:|---:|
| 工具描述（`description` 字段，每条一句） | 1,428 | 8% |
| **参数结构（`parameters`）** | **12,388** | **73%** |
| 名字、caps 等信封 | ~3,200 | 19% |

**先砍描述是错的方向**：全部 41 条描述加起来才 1,428 字，砍一半也只省 4%。

真正肥的是参数 JSON——而且大头不是文字，是 `"description":` 这个**键**本身：

```
把参数里所有 description 键去掉：17,007 → 10,384 字节（省 39%）
把每条的 description 截到 24 字： 17,007 → 16,170 字节（省 5%）
```

差 34 个百分点的原因是：每个参数都要付 `"description":""` 这 20 来字节的**壳**，
跟里面写几个字关系不大。

## 最肥的五个（都在「四合一」模块里）

| 工具 | 总字节 | 其中参数 |
|---|---:|---:|
| `team_task_update` | 1,027 | 898 |
| `ask_user_question` | 927 | 814 |
| `update_goal` | 855 | 718 |
| `schedule_create` | 845 | 721 |
| `schedule_update` | 782 | 670 |

## A/B：省字节会不会让模型填错参数

加了 `--tool-schema-compact`（投影时去掉参数说明，结构一个不动）。

**任务 1｜建任务**（三个参数，简单）：

```
完整表  input=11,600  tool_calls=1   ← 参数全对
压缩表  input= 8,843  tool_calls=1   ← 参数全对
```

**省 24%，结果一样。**

**任务 2｜建 + 认领 + 完成**（`action` 有七个枚举值）：

两种表都跑对，各 3 次调用。

**任务 3｜认领但不给 `owner`**（专门考验参数说明）：

```
完整表  → {"action":"claim","owner":"dsh-go"}     ← 说明里写着"claim 必填 owner"，模型自己填了
压缩表  → {"action":"claim"}                      ← 少了 owner，被工具拒
        ← [ERR]，然后多跑两轮才补上（tool_calls=4，input 反而更高）
```

**这次压缩表输了。**

## 结论：改工具，而不是改表

任务 3 暴露的不是"表压得不对"，而是**工具本来就该有默认值**：

> 认领时的身份就在 `ctx` 里（`spi.SessionFrom`），为什么还要模型填一遍？

改成"不给 owner 就用当前会话 id 认领"之后复测：

```
压缩表 + claim 不给 owner → [ok]，tool_calls=2，input=13,532
```

**要求写进参数说明，是把自己的设计债推给模型的上下文预算。**

## 第二刀：把"可推导的参数"变成可选

顺着上面的思路，这一轮改了三个「本来就有默认值」的必填参数：

| 工具 | 原来必填 | 现在 | 依据 |
|---|---|---|---|
| `update_goal` | `goal_id` | 可省 | **一个会话只有一个目标**，用 `g.ID` 兜底；填了仍必须对上（防串目标） |
| `watch_ack` | `repo` | 可省 | 只盯了一个仓库时用它 |
| `watch_stop` | `repo` | 可省 | 同上；**有多个时必须指定**——猜错会把水位记到别人头上 |
| `schedule_update` | `id` | 可省 | 只有一条定时任务时用它 |
| `schedule_delete` | `id` | 可省 | 同上 |
| `job_output` | `job_id` | 可省 | 只有一个后台任务时用它 |
| `job_kill` | `job_id` | 可省 | 同上；有多个时**列出候选 id** 再拒绝 |

三条测试钉住边界（单仓库可省 / 多仓库必须指定 / 一个都没有时说清先登记）。

多条时的拒绝长这样（真机）：

```
← schedule_update [ERR]
Hint: schedule_update：这个会话有 2 条定时任务（sch-0001-2771、sch-0002-d763），id 必须填一个
```

**拒绝时把候选 id 列出来**，模型下一句就能直接重试对；只说"id 必填"等于让它再跑一次 list。

真机（`job_output` / `job_kill` 都不带 id）：

```
→ bash {"command": "sleep 20; echo done-sleep", "idle_seconds": 3}
→ job_output {}                     ← [ok]  自动落到唯一那个任务
→ job_kill {"reason": "..."}        ← [ok]
```

**A/B 复测**（同两个任务，两种表）：

```
完整表  create 17,714 → 2 次调用，全对
压缩表  create 13,586 → 2 次调用，全对（-23%）
```

加上上一轮的「claim 默认认领到会话」，压缩表现在 **4/4 任务全对**。

## 20 次 A/B：把压缩表变成默认

`scripts/tool-table-ab.py`：10 个真实任务 × 两种表，判定三条（要求的工具确实被调用 /
全程没有 [ERR] / 没撞满步数）。

```
完整表: 9/10 正确，合计 input=199,112
压缩表: 9/10 正确，合计 input=155,853    ← 省 22%
```

（唯一失败的「盯仓库」两种表都失败——我的提示词里写的是占位符 `owner/name`，
模型去调 `repo_here` 看真名了。**这是我的任务写得不对，不是表的问题**。）

于是 `--tool-schema` 的默认值翻成 `compact`，要完整表得显式写 `--tool-schema=full`
（排查"模型没填对参数"时用）。

### 为什么这次敢翻默认

上一轮只有 3 个任务、还挂了一次「claim 漏 owner」，那时翻默认就是拍脑袋。
这一轮翻默认的前提是**先把这个漏填修掉**（认领默认到会话），再拿 20 次采样确认没有新回归。

顺序不能反：先改设计，再压表，最后才敢调默认。反过来就是拿默认值赌运气。

## 现状与下一步

- `--tool-schema-compact` 已可用，**默认仍是完整表**——样本还太少（3 个任务），
  不足以改默认。
- 想继续省，按代价排序：
  1. 继续给工具**加合理默认值**，让参数说明变得可有可无（本轮的 `claim`）
  2. 合并低频工具的 envelope（四合一 → 一带 action），但会破坏对 DSH 的契约对拍
  3. 按模式裁剪：给一个"精简"模式，只给常用十几个工具

相关：[`docs/token-budget.md`](token-budget.md)（工具**回显**占上下文的账，是另一个问题）。

## 防止默认值被悄悄改坏

默认值这种东西，坏起来是无声的：没人会为了"把 compact 改回 full"专门开个 PR，
但总有人为了排查一个 bug 顺手改一行，然后忘了改回来。

两道闸：

1. **`TestCompactTableKeepsContract`**（`cmd/dshd/tool_schema_test.go`）：
   逐个工具比对压缩前后的结构（去掉 description 后必须**完全相等**）。
   少一个 `required`、少一个 `enum`，这条就红。
   顺带报数：**41 个工具，参数区 16,088 → 7,167 字节（省 55%）**。

2. **`scripts/check.sh` 里两行**：
   - `dshd run --help` 必须出现 `default "compact"`，否则 FAIL
   - 工具表体积超过 32 KB 打 WARN（不是 FAIL——加工具当然会变大，
     但它必须**显式**变大，而不是悄悄涨到没人注意）

## 2026-11-04 复测：**预算用掉 92%，该动刀了**

工具数从 P0 那会儿的 41 个涨到 **57 个**，实测（走真网关，`usage.prompt_tokens`）：

| 口径 | 值 |
|---|---|
| 工具表（compact，默认） | 21,298 → **9,391 字节** |
| 真实 prompt_tokens（带这张表、消息只有 "hi"） | **5,532** |
| P0 定的上限 | 6,000 |
| **余量** | **468 token（7.8%）** |

也就是说：**再加两个"一个文件四个工具"的模块就会击穿**。而且这是**默认压缩表**的数字，
不是完整表——完整表更贵。

### 下一个杠杆在哪（按性价比排）

1. **参数区的 `description`**：上一轮量过，去掉它能省 **39%**。代价是模型看参数含义只能靠名字。
   现在这张表里参数描述仍是大头——它比"工具描述"贵得多（描述合计才 1,400 多字）。
2. **合并同族工具**：`watch_*` 五个、`hindsight_*` 六个、`team_task_*` 四个，
   每个都带一份完整 schema。合成"一个工具带 action 参数"能省一半以上，代价是参数校验变复杂。
3. **缩短 `Description()`**：现在上限 120 字，实际中位数远低于它，收益有限（上一轮量到只省 5%）。

### 为什么现在写下来而不是等击穿

这张表是**每轮都要付的钱**：一次任务的系统提示里它占 5,532 token，而模型可能只调其中两三个工具。
涨到 6,000 之后不是"再多一点点"，而是**每个会话的固定成本**再涨一档。
写在这里，是为了让下一个加工具的人先看到这笔账，而不是加完才发现。

### 钱具体花在哪（2026-11-04 分段实测）

| 项 | 字节 | 占比 |
|---|---|---|
| 参数区（schema 骨架） | 9,391 | **76%** |
| 工具描述（`Description()`） | 2,221 | 18% |
| 工具名 | 700 | 6% |
| 合计 | 12,312 | 100% |

**结论和直觉相反**：不是"我们的描述写太长"，是 **JSON schema 骨架本身就贵**。
所以"把 Description 再写短点"这种整法救不了预算（上限 120 字，中位数远低于它）。

按单工具体积排前八（含名字+描述+参数）：

```
626  ask_user_question      574  team_task_update     556  schedule_create
535  update_goal            492  schedule_update      445  todo_write
412  github                 410  watch_start
```

前八名里 **schedule_* 两个、watch_* 一族**都是"一个能力被拆成多个工具"的形状——
它们共享同一批参数（cron/timezone/agent 之类），每个都完整复制一份 schema。
这是唯一一处"合并能真的省下大块"的地方；但合并会改模型看到的接口，
属于 R4 契约变更，得先改文档、再动代码、再 A/B 验证模型是否还能正确调用。

## 2026-11-04：`--tools-mode merged` 实测 —— **假设被推翻，不要改默认**

按上面"合并同族工具能省大块"的推测，做了 `--tools-mode merged`（默认关闭）：
把 `watch_*`(5) / `hindsight_*`(5) / `schedule_*`(4) / `team_task_*`(4) 合成四个带 `action` 的工具，
57 个工具变 43 个，序列化 29,940 → 26,239 字节。

**然后 12 个真实任务 A/B（真网关、同一模型）：**

| 模式 | 选对且跑通 | 严格正确 | 首步 prompt 均值 | 全程 input token |
|---|---|---|---|---|
| compact（默认） | **12/12** | 11/12 | 7,925 | **241,492** |
| merged | **0/12** | 0/12 | 7,351 | **308,332** |

三条结论，一条比一条重要：

1. **合并确实省了首步**（7,925 → 7,351，-7%）。
2. **但正确率是 0。** 模型能选出 `team_task`，却在 `action:"list"` 之后**不信结果**，
   接着连开四个 `bash` 去 `grep PLAN.md` 找"看板"——它把"调了没得到想要的"理解成"我得自己去翻文件"。
3. **所以全程反而更贵**（241k → 308k，**+28%**）。省下的那 574 token/轮，
   被"选错 → 自查 → 再选错"的循环吃掉还有余。

**这就是为什么这一项必须真机 A/B 而不是看字节数**：从"工具表小了 12%"推到"上下文更省"，
中间隔着一个模型行为假设，而那个假设是错的。**merged 保留为可选实验，默认仍是 compact。**
