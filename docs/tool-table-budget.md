# 工具表的钱花在哪：一次预算审计

工具表 41 个 / 17,007 字节 / **5,451 token**（P0 定的上限 6k，已用掉 91%）。

再加两个「一个文件四个工具」的模块就会击穿。这一轮先算清楚钱花在哪，再谈怎么省。

## 钱花在 JSON，不在散文

| 组成 | 字节 | 占比 |
|---|---:|---:|
| 工具描述（`description` 字段，每条一句） | 1,428 | 8% |
| **参数结构（`parameters`）** | **12,388** | **73%** |
| 名字、caps 等信封 | ~3,200 | 19% |

**先砍描述是错的方向**：全部 41 条描述加起来才 1,428 字，砍一半也只省 4%。

真正肥的是参数 JSON——而且大头不是文字，是 `"description":` 这个**键**本身：

```
把参数里所有 description 键去掉：17,007 → 10,384 字节（省 39%）
把每条的 description 截到 24 字： 17,007 → 16,170 字节（省 5%）
```

差 34 个百分点的原因是：每个参数都要付 `"description":""` 这 20 来字节的**壳**，
跟里面写几个字关系不大。

## 最肥的五个（都在「四合一」模块里）

| 工具 | 总字节 | 其中参数 |
|---|---:|---:|
| `team_task_update` | 1,027 | 898 |
| `ask_user_question` | 927 | 814 |
| `update_goal` | 855 | 718 |
| `schedule_create` | 845 | 721 |
| `schedule_update` | 782 | 670 |

## A/B：省字节会不会让模型填错参数

加了 `--tool-schema-compact`（投影时去掉参数说明，结构一个不动）。

**任务 1｜建任务**（三个参数，简单）：

```
完整表  input=11,600  tool_calls=1   ← 参数全对
压缩表  input= 8,843  tool_calls=1   ← 参数全对
```

**省 24%，结果一样。**

**任务 2｜建 + 认领 + 完成**（`action` 有七个枚举值）：

两种表都跑对，各 3 次调用。

**任务 3｜认领但不给 `owner`**（专门考验参数说明）：

```
完整表  → {"action":"claim","owner":"dsh-go"}     ← 说明里写着"claim 必填 owner"，模型自己填了
压缩表  → {"action":"claim"}                      ← 少了 owner，被工具拒
        ← [ERR]，然后多跑两轮才补上（tool_calls=4，input 反而更高）
```

**这次压缩表输了。**

## 结论：改工具，而不是改表

任务 3 暴露的不是"表压得不对"，而是**工具本来就该有默认值**：

> 认领时的身份就在 `ctx` 里（`spi.SessionFrom`），为什么还要模型填一遍？

改成"不给 owner 就用当前会话 id 认领"之后复测：

```
压缩表 + claim 不给 owner → [ok]，tool_calls=2，input=13,532
```

**要求写进参数说明，是把自己的设计债推给模型的上下文预算。**

## 第二刀：把"可推导的参数"变成可选

顺着上面的思路，这一轮改了三个「本来就有默认值」的必填参数：

| 工具 | 原来必填 | 现在 | 依据 |
|---|---|---|---|
| `update_goal` | `goal_id` | 可省 | **一个会话只有一个目标**，用 `g.ID` 兜底；填了仍必须对上（防串目标） |
| `watch_ack` | `repo` | 可省 | 只盯了一个仓库时用它 |
| `watch_stop` | `repo` | 可省 | 同上；**有多个时必须指定**——猜错会把水位记到别人头上 |
| `schedule_update` | `id` | 可省 | 只有一条定时任务时用它 |
| `schedule_delete` | `id` | 可省 | 同上 |
| `job_output` | `job_id` | 可省 | 只有一个后台任务时用它 |
| `job_kill` | `job_id` | 可省 | 同上；有多个时**列出候选 id** 再拒绝 |

三条测试钉住边界（单仓库可省 / 多仓库必须指定 / 一个都没有时说清先登记）。

多条时的拒绝长这样（真机）：

```
← schedule_update [ERR]
Hint: schedule_update：这个会话有 2 条定时任务（sch-0001-2771、sch-0002-d763），id 必须填一个
```

**拒绝时把候选 id 列出来**，模型下一句就能直接重试对；只说"id 必填"等于让它再跑一次 list。

真机（`job_output` / `job_kill` 都不带 id）：

```
→ bash {"command": "sleep 20; echo done-sleep", "idle_seconds": 3}
→ job_output {}                     ← [ok]  自动落到唯一那个任务
→ job_kill {"reason": "..."}        ← [ok]
```

**A/B 复测**（同两个任务，两种表）：

```
完整表  create 17,714 → 2 次调用，全对
压缩表  create 13,586 → 2 次调用，全对（-23%）
```

加上上一轮的「claim 默认认领到会话」，压缩表现在 **4/4 任务全对**。

## 20 次 A/B：把压缩表变成默认

`scripts/tool-table-ab.py`：10 个真实任务 × 两种表，判定三条（要求的工具确实被调用 /
全程没有 [ERR] / 没撞满步数）。

```
完整表: 9/10 正确，合计 input=199,112
压缩表: 9/10 正确，合计 input=155,853    ← 省 22%
```

（唯一失败的「盯仓库」两种表都失败——我的提示词里写的是占位符 `owner/name`，
模型去调 `repo_here` 看真名了。**这是我的任务写得不对，不是表的问题**。）

于是 `--tool-schema` 的默认值翻成 `compact`，要完整表得显式写 `--tool-schema=full`
（排查"模型没填对参数"时用）。

### 为什么这次敢翻默认

上一轮只有 3 个任务、还挂了一次「claim 漏 owner」，那时翻默认就是拍脑袋。
这一轮翻默认的前提是**先把这个漏填修掉**（认领默认到会话），再拿 20 次采样确认没有新回归。

顺序不能反：先改设计，再压表，最后才敢调默认。反过来就是拿默认值赌运气。

## 现状与下一步

- `--tool-schema-compact` 已可用，**默认仍是完整表**——样本还太少（3 个任务），
  不足以改默认。
- 想继续省，按代价排序：
  1. 继续给工具**加合理默认值**，让参数说明变得可有可无（本轮的 `claim`）
  2. 合并低频工具的 envelope（四合一 → 一带 action），但会破坏对 DSH 的契约对拍
  3. 按模式裁剪：给一个"精简"模式，只给常用十几个工具

相关：[`docs/token-budget.md`](token-budget.md)（工具**回显**占上下文的账，是另一个问题）。

## 防止默认值被悄悄改坏

默认值这种东西，坏起来是无声的：没人会为了"把 compact 改回 full"专门开个 PR，
但总有人为了排查一个 bug 顺手改一行，然后忘了改回来。

两道闸：

1. **`TestCompactTableKeepsContract`**（`cmd/dshd/tool_schema_test.go`）：
   逐个工具比对压缩前后的结构（去掉 description 后必须**完全相等**）。
   少一个 `required`、少一个 `enum`，这条就红。
   顺带报数：**41 个工具，参数区 16,088 → 7,167 字节（省 55%）**。

2. **`scripts/check.sh` 里两行**：
   - `dshd run --help` 必须出现 `default "compact"`，否则 FAIL
   - 工具表体积超过 32 KB 打 WARN（不是 FAIL——加工具当然会变大，
     但它必须**显式**变大，而不是悄悄涨到没人注意）

## 2026-11-04 复测：**预算用掉 92%，该动刀了**

工具数从 P0 那会儿的 41 个涨到 **57 个**，实测（走真网关，`usage.prompt_tokens`）：

| 口径 | 值 |
|---|---|
| 工具表（compact，默认） | 21,298 → **9,391 字节** |
| 真实 prompt_tokens（带这张表、消息只有 "hi"） | **5,532** |
| P0 定的上限 | 6,000 |
| **余量** | **468 token（7.8%）** |

也就是说：**再加两个"一个文件四个工具"的模块就会击穿**。而且这是**默认压缩表**的数字，
不是完整表——完整表更贵。

### 下一个杠杆在哪（按性价比排）

1. **参数区的 `description`**：上一轮量过，去掉它能省 **39%**。代价是模型看参数含义只能靠名字。
   现在这张表里参数描述仍是大头——它比"工具描述"贵得多（描述合计才 1,400 多字）。
2. **合并同族工具**：`watch_*` 五个、`hindsight_*` 六个、`team_task_*` 四个，
   每个都带一份完整 schema。合成"一个工具带 action 参数"能省一半以上，代价是参数校验变复杂。
3. **缩短 `Description()`**：现在上限 120 字，实际中位数远低于它，收益有限（上一轮量到只省 5%）。

### 为什么现在写下来而不是等击穿

这张表是**每轮都要付的钱**：一次任务的系统提示里它占 5,532 token，而模型可能只调其中两三个工具。
涨到 6,000 之后不是"再多一点点"，而是**每个会话的固定成本**再涨一档。
写在这里，是为了让下一个加工具的人先看到这笔账，而不是加完才发现。

### 钱具体花在哪（2026-11-04 分段实测）

| 项 | 字节 | 占比 |
|---|---|---|
| 参数区（schema 骨架） | 9,391 | **76%** |
| 工具描述（`Description()`） | 2,221 | 18% |
| 工具名 | 700 | 6% |
| 合计 | 12,312 | 100% |

**结论和直觉相反**：不是"我们的描述写太长"，是 **JSON schema 骨架本身就贵**。
所以"把 Description 再写短点"这种整法救不了预算（上限 120 字，中位数远低于它）。

按单工具体积排前八（含名字+描述+参数）：

```
626  ask_user_question      574  team_task_update     556  schedule_create
535  update_goal            492  schedule_update      445  todo_write
412  github                 410  watch_start
```

前八名里 **schedule_* 两个、watch_* 一族**都是"一个能力被拆成多个工具"的形状——
它们共享同一批参数（cron/timezone/agent 之类），每个都完整复制一份 schema。
这是唯一一处"合并能真的省下大块"的地方；但合并会改模型看到的接口，
属于 R4 契约变更，得先改文档、再动代码、再 A/B 验证模型是否还能正确调用。

## 2026-11-04：`--tools-mode merged` 实测 —— **省表是真的，但不建议改默认**

按上面"合并同族工具能省大块"的推测，做了 `--tools-mode merged`（**默认关闭**）：
把四个族的 **17 个**工具合成 4 个带 `action` 的工具（`watch_doctor` 没并进来，理由见下）。
执行侧一个字节没动——合并只发生在"把工具表发给模型"这一层（`cmd/dshd/tool_merged.go`）。

> **更正（同日第二次测量）**：本节的"正确率 0/12"是 A/B 脚本的一个 bug 造成的误判。
> merged 下 stderr 打的是**模型看到的名字**（`team_task`），脚本却拿原工具名
> （`team_task_list`）去对结果行，于是每一次都判成"没跑通"。修掉名字对齐后重跑
> 72 次（12 任务 × 2 表 × 3 采样），真实数字是 **36/36 vs 34/36**，整轮 +6.3% 而不是 +28%。
> 下面全部换成修正后的数据；旧结论（"正确率 0"）保留这次的更正记录，不要再引用。

### 表到底小了多少

| 口径 | compact（默认） | merged |
|---|---:|---:|
| 工具数 | 57 | **44** |
| `dshd tools` 打印字节（缩进） | 29,940 | **27,055（−9.7%）** |
| 发给模型的 tools JSON（无缩进） | 19,558 | **17,671（−9.6%）** |
| 本仓估算器（`EstimateRunes`） | 5,269 token | **4,791 token（−9.1%）** |
| 真网关 `usage.prompt_tokens` / 步（12 任务均值） | 7,926 | **7,462（−5.9%）** |

口径差得远是因为：工具表只占一轮输入的一部分（系统提示 + 历史 + 这张表），
表省 9% ≈ 整轮输入省 6%。**每步稳定少付约 470 token**，12 个任务的 36 对样本上一致。

### 正确率与总账（72 次真网关调用）

`scripts/tool-table-merged-ab.py`：12 个任务 × 2 种表 × 3 次采样。

| | compact | merged |
|---|---|---|
| 关键工具选对且跑通 | **36/36** | **34/36** |
| 一次过（无 ERR、无多余调用） | 34/36 | 33/36 |
| 一轮 12 任务总和（每任务 3 次均值） | **248,064** | 263,780（**+6.3%**） |

拆开看，账是两笔：

- **步数不变的任务（10/12）**：merged 每个任务净省 900–1,400 token（例：建任务 16,027 → 15,113，
  建并认领 24,331 → 22,988）。这一档合并是稳赚的——省的就是每步那 470。
- **步数变多的任务（2/12）**：看板 3.3 → 4.7 步、盯仓库 2.7 → 4.0 步。
  多一步≈多付 7,400 token，一次就把三个任务的收益吃回去。

两次失败都在这两个任务上，且都不是"选错 action"：

1. **看板**：`team_task(action="list")` 跑通了、返回空看板，模型**不信这个结果**，
   接着 bash/read 去翻 `PLAN.md` 找"看板"——它把"空的"理解成"我得自己去翻文件"。
2. **盯仓库**：`watch(action="start")` 之后环境没有 gh 登录，模型转去 `watch_doctor` /
   `github` / `bash` 查 gh 状态，6 步用满。

所以真正的成本不是"选错 action"，而是 **merged 把 18 个工具收成 4 个之后，
模型少了一条"换个明确的小工具再试一次"的退路**——它只能靠通用工具（bash/grep/github）自救，
而那条路又贵又容易打转。

### 设计上踩到的四个坑（都已落到代码/测试里）

1. **`required` 只能写交集** → 每个 action 的必填在表里消失了。实测模型真的漏：
   `team_task(action="create", subject="A")` 少了 `description`，而 `team_task_create`
   自己不校验，于是**静默建了一条没描述的任务**，模型再花四步去补。
   现在由路由按每个 action 自己的 required 校验（`required` 进 `mergedAction.Required`），
   缺了当场报错并点名——代价是"补一轮"，但不会再错着往下走。
2. **参数是并集** → 给错 action 的参数会撞工具的"多余参数"（实测 `list_knowledge_pages` 带了 `limit`）。
   这个只能靠描述里的"哪个 action 要哪些参数"兜，兜不住就多一轮。
3. **成员 schema 不可信** → `watch_doctor` 的 schema 是 `watch_ack` 的复制（`required:["numbers"]`，
   体检根本不看编号）。合进来只有"逼模型编编号"和"无视 schema"两条路，**两个都不干**：
   它留在表外，名字不变。这一条直接决定了 43 → 44 个工具。
4. **参数别名** → `hindsight_read_knowledge_page` 的 schema 要求 `page_id`，
   但它自己写着"`id` 也行"。路由的必填校验认别名（`mergedAction.Aliases`），
   否则合并层会比原工具更严——那等于改了工具行为。

### 结论

**不建议现在改默认。** 理由不是"正确率掉了 2 条"，而是：

- 省的钱（每步 470 token）与亏的钱（多一步 7,400 token）不在一个量级上；
- 触发多步的不是 schema 写错，而是"小工具没了"这件事本身——换描述写法治不了；
- 两个任务上的退化是**环境相关**的（没有 gh 登录 / 空看板），恰恰是真实使用中最常见的情形。

如果以后要翻默认，前提是三条同时成立：① 每个 action 的必填在表里可表达（或路由校验覆盖到）；
② "工具结果为空/失败"时模型有明确指引，不会转去翻文件；③ ≥30 次采样正确率不降。
在这三条之前，它就是一个**可以显式打开的实验档**：`--tools-mode merged`。

## 2026-11-04 第三刀：参数区 9,391 → 8,535，模型看到的信息一个字节没少

merged 那节证明了一件事：**改接口**（把 18 个工具收成 4 个）确实省表，但两条退化的任务
多跑一步就把收益吃回去大半——省下的 token 不在一个量级上。

这一节换一条完全不碰接口的路：工具名、参数名、描述、enum、required 全部不动，
**只改 JSON 的写法**——把参数区里"接口已经规定 / 省略等于默认"的骨架去掉。

### 先量：9,391 字节到底花在哪（`scripts/tool-table-anatomy.py`)

脚本逐字节记账：每个键、每个值、每个标点都归到一个桶，**各桶相加必须等于参数区总字节**
（不等就非零退出，绝不打印一张对不上账的表）。

复现这两张账：

```bash
python scripts/tool-table-anatomy.py --pre-tighten   # 收紧前的 compact（9,391）
python scripts/tool-table-anatomy.py                 # 现在的默认表（8,535）
```

`--pre-tighten` 是拿 `--schema full` 的表**照旧实现的做法**只删 `description` 键
（包括连名叫 `description` 的参数一起删），所以能在改造之后仍然量出 9,391。

compact 表的账：

| 类别 | 字节 | 占比 | 是什么 |
|---|---:|---:|---|
| 结构键 | 4,373 | 46.6% | `"type"`/`"properties"`/`"required"`/`"additionalProperties"` 的键名+冒号 |
| 类型值 | 1,633 | 17.4% | `"string"`/`"integer"`/`"object"`… |
| 参数名 | 1,322 | 14.1% | properties 里的 130 个参数名 |
| 标点 | 944 | 10.1% | 花括号、方括号、逗号 |
| required 引用 | 503 | 5.4% | required 数组里又抄一遍的参数名 |
| 约束值 | 333 | 3.5% | minimum/maximum/format |
| 枚举值 | 283 | 3.0% | 34 个 enum 取值 |
| **合计** | **9,391** | 100% | |

按骨架词排（"整段"= 键 + 冒号 + 它直接带的值）：

| 骨架词 | 出现 | 字节 | 占比 |
|---|---:|---:|---:|
| `"additionalProperties":false` | 59 | 1,652 | 17.6% |
| `"type":"string"` | 93 | 1,395 | 14.9% |
| 参数名（properties 的键） | 130 | 1,322 | 14.1% |
| 标点（花括号/方括号/逗号） | 312 | 944 | 10.1% |
| `"type":"object"` | 62 | 930 | 9.9% |
| `"properties":` | 61 | 793 | 8.4% |
| required 数组元素（重复的参数名） | 57 | 503 | 5.4% |
| `"required":` | 40 | 440 | 4.7% |
| `"type":"integer"` | 21 | 336 | 3.6% |
| enum 值 | 34 | 283 | 3.0% |

### 数字给出的结论：能去的只有 11.8%

**可去且语义不变的 1,112 字节（11.8%）**：

| 可去的 | 个数 | 字节 | 为什么语义不变 |
|---|---:|---:|---|
| 顶层 `"type":"object"` | 57 | 912 | function calling 的 `parameters` 必须是对象，这是接口规定 |
| 空 `"properties":{}` | 9 | 144 | 省略与空等价 |
| `"additionalProperties":true` | 2 | 56 | JSON Schema 的默认值就是 true（2 处都在嵌套层，只查顶层会漏） |

剩下 88.2% 是语义，动不得。特别要说明最大的一块：
**`"additionalProperties":false` 占 1,652 字节（17.6%），但它是真约束**。
删掉它等于告诉模型"可以带别的参数"——那不是压缩，是改契约，所以不做。

这也解释了为什么"再压一点"很难：参数区已经不是散文，是**参数名 + 类型 + 约束**本身。

### 为什么 11% 的字节能省 5–6% 的 token

JSON 骨架是标点密集的短 token（`{`、`"`、`:`、`,`），每个字节比中文描述**贵**得多。
真网关配对实测（同一批请求里两种表交替跑，各 4 次，消息只有 "hi"）：

```
旧 compact  5,485 prompt_tokens
新 compact  5,158 prompt_tokens     ← -327 token（-6.0%）
```

> 口径提醒：网关的 `prompt_tokens` 有**批间漂移**（同一张表在不同批次里见过
> 5,330 / 5,485 / 5,532），所以只认**同一批里的配对差**，别拿跨批的绝对值相减。
> 上一节记的 5,532 是某一批的冷启动值，不是"旧表更贵"。

### 真机 A/B：12 个任务 × 两种表

`scripts/tool-table-tight-ab.py`（12 个真实任务，两个**二进制**各跑一遍——
"旧 compact"只存在于旧二进制里，所以按 exe 分档，不按 flag 分档）。
跑两轮，合计每档 36 次：

| 模式 | 关键工具跑通 | 一次过 | 第一步 input 均值 | 全程 prompt_tokens |
|---|---:|---:|---:|---:|
| 旧 compact | **35/36** | 34/36 | 8,115 | 762,454 |
| 新 compact | **35/36** | 33/36 | **7,676（−5.4%）** | **731,340（−4.1%）** |

- 关键工具全跑通的次数**一样**（35/36）。唯一那一条是「盯仓库」：环境里没有 `gh` 登录，
  模型转去 `watch_doctor`/`github`/`bash` 查状态，6 步用满——和表无关（merged 那节记过同一个坑）。
- "一次过"差的一条是模型多调了一次 `grep`/`watch_status` 自查，不是参数填错；
  同类抖动在旧表上也出现过（第一轮旧表在「存记忆」上多调了一次）。
- **第一步均值少 439 token（−5.4%）**：这是**每步都要付**的钱，不是一次性收益。
  整轮百分比（−4.1%）会被"模型这轮多跑几步"放大或抵消，所以以第一步为准。

**正确率没有掉。**

### 顺手抓到一个真 bug：compact 把名叫 `description` 的参数删了

`internal/agent.CompactSchema` 是"见到 `description` 键就删"，它分不清
**schema 上的说明注解** 和 **名叫 `description` 的参数**。本仓有 8 个工具真有这个参数
（`ask_user_question` 的 `options[]`、`bash`、`present`、`spawn_teammate`、`subagent`、
`subagent_fork`、`team_task_create`、`team_task_update`），一共 8 个参数。

删掉的后果不是"少一行说明"，是 **`required` 里还点着它、`properties` 里却没有**：
模型看到一个"必填、但没类型也没说明"的名字，只能靠猜。这正是这次任务要防的那种信息丢失。

新投影把两件事分开处理：

- schema 对象上的 `description` = 注解 → 删；
- `properties` 映射里的键 = 参数名 → 原样保留，哪怕它就叫 `description`。

补回来 +256 字节（8 个参数）：9,391 − 1,112 + 256 = **8,535**。

### 做了什么（没有新增开关）

`compact` 的语义改成**"去参数说明 + 去冗余骨架"**，不新增 `--tools-mode` 值：

- 合并（`merged`）改的是**模型看到的接口**（工具名、action），属于 R4 契约变更，必须显式打开；
- 收紧只改 JSON 写法，解析出来的语义逐条相等——它就是 `compact` 本该有的样子。
  再多一个开关，只会让人选错。

落点都在 `cmd/dshd/`：

| 文件 | 改动 |
|---|---|
| `tool_merged.go` | `tightenTable` / `tightenSchema` / `tightenObject`：投影层（去注解、去冗余骨架）。用 `json.RawMessage` 承载子节点，type 取值/枚举/数字逐字节不动 |
| `main.go` | `cmdRun` 在 merged 之后套 `tightenTable`（顺序不能反：合并要读成员原始 schema）；`cmdTools` 走同一条链；`CompactTools: false`（见下） |
| `tool_schema_test.go` | `TestCompactTableKeepsContract` 改成逐工具比对**归一化后的结构**；新增 `TestTightSchemaKeepsDescriptionParam`、`TestRequiredParamsAreDeclared`、`TestTightTableIsAThinWrapper` |

两个容易踩的坑，都钉在测试里：

1. **顺序**：`tightenTable` 必须在 `newMergedTable` **之后**。合并要读成员的原始 schema
   （顶层 `type` 判断、required 抄写），先收紧会让它把"顶层不是 object"误判成合不进来。
2. **别让循环再压一遍**：`agent.Loop.CompactTools` 那个 `CompactSchema` 就是删掉
   `description` 参数的那把钝刀。表在 `cmdRun` 里已经投影完，所以这里显式关掉——
   否则后一遍会把前一遍刚补回来的参数又删掉。

### 候选 B：`$ref` + `definitions`（不做）

同一个参数 schema 在不同工具里反复出现：`{"type":"string"}` 出现 77 次（1,309 字节）。
但 **OpenAI 兼容接口的每个 function 各带一份 `parameters`，没有跨工具的 `definitions` 可引用**：

```
跨工具重复：2,148 字节   ← $ref 用不上
同一工具内重复：667 字节 ← $ref 唯一可能生效的地方，还要减去每个工具新增的定义块
```

在同一个工具内部做 `$ref`，净收益是"667 减去定义块"，而定义块本身要写
`"$defs":{"s":{"type":"string"}}` 这样的骨架——量级相同，还多一个网关可能不认的语法。
**结论：不做。** 想省这块只能等协议支持共享定义，或者在客户端侧展开。

### 候选 C：按需装载（本轮只验可行性，不实现）

现在 57 个工具全部常驻。`tool-table-anatomy.py` §5 的粗算（信封按 40 字节/个估）：

| 藏起 | 藏起的字节 | 目录（只列名字） | 净省 | 目录带一句话 | 净省 |
|---|---:|---:|---:|---:|---:|
| 27 个最小的（对按需最不利） | 4,485 | 427 | **4,058（29%）** | 1,500 | 2,985（21%） |
| 27 个最大的（最有利） | 8,759 | 383 | **8,376（60%）** | 1,590 | 7,169（51%） |

但这条路能不能成，取决于一个行为假设，而不是字节数：

> **模型怎么知道"有个工具叫 hindsight_ingest_document，需要时去拉"？**

至少要有三个条件同时成立，它才会去拉：

1. **目录里能看出"该拉"**：只有名字不够，得有一句话说明（27 个名字+描述 = 1,500 字节，
   净省降到 2,985 字节 / 21%）。名字叫 `github` 的还好，叫 `job_output` 的就未必。
2. **规则要写进系统提示，而不是工具描述里**：被藏起来的工具，它的描述也一起藏起来了，
   "什么时候用我"这句话没有地方放。只能在系统提示里写一条"遇到 X 先 tool_load"，而这条
   又要占字节，且**模型不一定照做**——merged 那节的实测就是反例：`team_task(action=list)`
   返回空看板，模型不信，转去 `bash`/`grep` 翻文件。
3. **拉取本身要便宜**：一次 `tool_load` = 一次工具调用（模型输出）+ 一份 schema 回填
   （工具结果），约等于把省的字节又付回去一次。只有"大多数会话根本不碰这 27 个工具"时才划算。

**结论：可行性成立（工具表每步是重新发的，`toolDefs()` 每步都从表里构建，运行时换表没有结构障碍），
但收益完全取决于"模型会不会去拉"。** 要做得先回答：哪些工具在真实会话里 30 天内一次没被调用过？
拿不到这个分布，按需装载就是拿 21% 的表预算去赌模型的自救能力——和 merged 是同一类赌注。

### 结论：这刀可以留下

- 参数区 **9,391 → 8,535 字节（-9.1%）**，整张表 **16,531 → 15,675 字节（-5.2%）**；
- 真网关每步输入 **-330 ~ -440 token**：配对实测 5,485 → 5,158（-6.0%），
  12 任务 A/B 的第一步均值 8,115 → 7,676（-5.4%）。都是 `usage.prompt_tokens`，不是估算器；
- 预算账：5,158 / 6,000 = **86%**（原 5,532 / 6,000 = 92%），余量从 468 token 涨到 **842**；
- 模型看到的信息**逐工具语义相等**（`TestCompactTableKeepsContract` 归一化后 DeepEqual），
  并且**补回了 compact 原本会删掉的 8 个名为 `description` 的参数**；
- 没有新增模式、没有改接口，`merged` 仍是显式实验档。

`--tools-mode full` 保留原样：它现在的作用是"排查参数问题时的对照表"，
以及 `TestCompactTableKeepsContract` 里的那一侧基准。

### 下一个杠杆在哪（写清"没路了"和"还剩什么"）

参数区剩下的 88.2% 是语义。想在**不改信息**的前提下继续压，只有两条路，都不便宜：

1. **等协议支持共享定义**（`$ref`/`definitions` 跨 function 复用），能省跨工具的 2,148 字节；
2. **按需装载**（候选 C），上限 21%–51%，但要先拿到"哪些工具真的没人用"的分布。

按代价排序，下一刀应该先做**测量**而不是压缩：给 30 天会话日志统计每个工具的调用次数。
没有这个分布，任何"裁掉低频工具"的动作都是拿真实任务赌运气——merged 那两条退化的任务
就是赌输的样子。
