# subagent vs subagent_fork：一次对照读数（2026-11-03）

## 同一个问题，两种派法

问题：「dsh.toml 里的 version 变量是什么值」。

| | subagent | subagent_fork |
|---|---:|---:|
| 子代理步数 | 9 | 12 |
| 交回的字数 | 208 | 178 |
| 输入 token | 22935 | 30953 |
| 工具调用 | 2 | 3 |

## 读法

**fork 不是免费的：这次多花 35% 输入。**

道理很直白——它要把父会话最近 20 条塞进子代理的上下文。
换来的是"子代理知道刚才在聊什么"，代价是每派一次都付一遍历史钱。

## 但这份读数只能当方向，不能当结论

三条限制，写清楚免得被误用：

1. **样本各 1 次**，且两次的提示词措辞不同（一个写"派出去"，一个写"用 subagent_fork 派出去"）
2. 这个任务**根本不需要父会话上下文**——它对 fork 是不利的场景
3. 步数差异（9 vs 12）里混着模型随机性，不是 fork 造成的

## 所以给模型的指引只能是定性的

- 任务**依赖刚才的对话**（"接着上一轮""刚才那个文件"）→ `subagent_fork`
- 任务**自包含**（"查一下 dsh.toml 的 version"）→ `subagent`

这条已经写进两个工具的 Description 里：`subagent` 说"子代理看不到本会话的历史"，
`subagent_fork` 说"能看到本会话上下文"。**让模型按语义选，而不是按成本选**——
因为成本取决于任务，而语义是给定的。

## 下一次要量得更准的话

同一个任务、同一种措辞，各跑 5 次取中位数；任务本身要**需要上下文**
（比如"把我刚才说的暗号复述一遍"），否则量的是 fork 的纯开销，不是它的价值。

---

## 继承窗口有多大：实测（2026-11-03）

### 怎么测的

1. 起会话，第一条消息里说「记住暗号：青柠-77」
2. 用同一个会话连灌 **12 轮 filler**（每轮 user + assistant ≈ 24 条消息）
3. 再调 `subagent_fork`，让它回答「暗号是什么」

### 结果

```
← subagent_fork [ok] 带上下文子代理完成「问子代理暗号」（3 步，4 字）
不知道。
```

**4 个字 = 「不知道。」** —— 暗号已经在 20 条窗口之外，子代理诚实地说了不知道。

### 这个结果说明两件事

**好的一面**：窗口是真的有界，而且**越界时子代理会说不知道**，不会瞎编一个暗号。
这一点比"答对"更重要——假答案和没答案在界面上长得一样，但后果完全不同。

**不好的一面**：`keep = 20` 是我拍的数。实测说明它大约只能覆盖**最近 10 轮对话**
（每轮 user+assistant 两条）。长会话里派 fork，子代理拿不到早期上下文。

### 该怎么办（下一轮决定）

三条路，各有代价：

| 做法 | 代价 |
|---|---|
| 把 keep 调大（如 60） | 每次 fork 多付历史钱，长会话可能顶满子代理上下文 |
| 继承"最近 N 条 + 压缩摘要" | 要接 `internal/compact`，复杂度上一个台阶 |
| 保持 20，但在工具结果里**明确告诉模型**"只带了最近 20 条" | 零成本，但模型仍可能误以为子代理知道全部 |

**至少第三条现在就该做**：结果里说清带了多少条，模型才不会以为"派个 fork 它就知道一切"。

### 记一笔

我上一轮写"只验过答得出暗号"，这一轮验到了**它答不出的边界**。
一个能力只知道"能用"是不够的，还得知道**在哪里不能用**。
