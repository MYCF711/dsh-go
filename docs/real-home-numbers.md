## 查 `session.history` 为什么比 `load` 慢（同轮修好）

### 先隔离：结果为空也要 425 ms

```
session.history sinceSeq=0       519 ms   （返回全部消息）
session.history sinceSeq=∞       425 ms   （返回空）
```

空结果都 425 ms → **成本不在返回的数据量，在"投影之前把整份日志解出来"**。

### 原因

`HistorySession` 的实现是：

```go
all, err := src.Messages(sessionID)      // ← 全量投影
return SelectPage(all, PageSince, ...)   // 再按 seq 过滤
```

**先投影再过滤。** 而界面补洞时通常只要最后几条。

### 改法

加一个可选接口 `SeqSourcer`：宿主实现 `MessagesSince(id, sinceSeq)`，
**在投影前先把不需要的事件掐掉**。没实现这个接口的源仍然走老路（不破坏契约）。

### 改完的读数

| | 改前 | 改后 |
|---|---:|---:|
| history 结果为空 | 425 ms | **301 ms** |
| history 全量 | 519 ms | 521 ms |

**空结果快了 29%。** 全量没变——那条路本来就要把每条消息都返回。

### 剩下的 301 ms 是什么

不是投影了，是 `v4.ReadFile`：把 24k 事件的 zstd 全文解出来。
要再往下压，得像 `follow` 那样**按 offset 只读尾巴**——那是另一件事，没这轮做。

### 一个插曲

改完第一次跑探针时连接被重置，看起来像服务崩了。
手工用 curl 复现一次就通了，重跑探针也正常。**按清单第 1 条：失败先怀疑探针。**

## 同一把刀：`session.load` 也改成"只投影首屏"

`LoadSession` 原来是 `src.Messages()` 全量投影 → `SelectPage(PageTail)` 再截尾。
和 `history` 是同一个病：**先干完所有的活，再扔掉 99%。**

改法：加可选接口 `TailSourcer`（`MessagesTail(id, limit)`），宿主侧**从后往前只挑要投影的那 N 条**；
总数只数事件类型（不解 JSON），所以 counting 几乎免费。

| | 改前 | 改后 |
|---|---:|---:|
| `session.load` 最大会话（24k 事件） | 482 ms | **341 ms** |
| `session.load` 中位会话 | 28 ms | **21 ms** |

最大那份快了 **29%**，中位快了 25%。

### 为什么只快了 29% 而不是 10 倍

因为剩下的 341 ms 不是投影，是 `v4.ReadFile`——把 24k 事件的 zstd 全文解出来。
**投影只是第二位成本，读文件才是第一位。**

要真的到毫秒级，得让 `ReadFile` 也支持"从尾部往前读"（follow 那条路已经在做）。
那是个更大的改动，记在这里，不在这轮做。

### 这一轮的模式

history 和 load 是**同一个病**：先全量、再截断。
第二次修的时候几乎不用想，照着上一次的刀法切——**这就是把第一次修法写成文档的收益。**

## 能不能只读尾巴？能，但会破坏 `total`

拿最大的那份会话（**25 MB / 13,900 帧 / 全量解压 71.5 MB**）实测：

| 做法 | 耗时 |
|---|---:|
| 全量解压 13,900 帧 | **137.8 ms** |
| 只解最后 5 帧 | **0.5 ms** |

**帧之间互相独立**（每帧自带 magic），所以从尾部挑几帧解是可行的，差 **275 倍**。

### 为什么这轮没改

`session.load` 的返回里有 `total` 和 `truncated`——**要给出准确的总消息数，就必须数完所有帧**。
只读尾巴的话，`total` 要么变成近似值，要么消失。

这是一个**契约选择**，不是性能问题：

| 方案 | 代价 |
|---|---|
| 保持现状（341 ms） | 界面点开会话最多等三分之一秒 |
| 只读尾巴（≈1 ms） | `total` 变成 `<至少 N 条>` 或干脆去掉 |
| 两次：先读尾巴出首屏，再后台补 total | 复杂，但两边都满足 |

**我倾向第三个**，但要先确认界面到底拿 `total` 干什么（显示"共 210 条"？还是滚动条高度？）。
在没确认之前，**不动契约**——这正是 `AGENTS.md` §11 里"契约先行"那条。

### 顺带修正一个数

341 ms 里：**解压 138 ms + 解析与投影约 200 ms**。
之前说"主要成本是读文件"，更准确的说法是**解压与投影各占一半**。

### 记一笔

这一轮的价值是**把"能不能"变成了"能，但要付什么价"**。
下一轮如果有人问"为什么点开会话要三分之一秒"，这里有数；
如果有人问"能不能快 10 倍"，这里也有答案和它的代价。

## `total` 到底被用来干什么（去隔壁仓库查了）

`dsh-ui` 里只有一处用到：

```go
// dsh-ui/cmd/app/main.go:152
m.status = fmt.Sprintf("%s · %d 条（总 %d）· 温缓存", cs.title, len(cs.msgs), cs.total)
```

**只是状态栏上的一行字**——不是滚动条高度、不是分页依据、不是任何逻辑依赖。

### 所以「两段式」是安全的

| 阶段 | 给什么 | 耗时 |
|---|---|---:|
| 第一段 | 首屏 50 条（从尾部几帧解出来） | **≈1 ms** |
| 第二段 | `total` 稍后补上（全量解压） | ≈140 ms |

界面先有内容、状态栏数字晚半秒出现——**没有任何逻辑会因此出错**。

### 但这轮仍然没动手

原因不是技术，是**跨仓契约**：`total` 从"必填且同步"变成"可能迟到"，
那边 `Truncated` 的判断（`len(msgs) < total`）也要跟着改。
这属于 `AGENTS.md` §11 的「契约先行」——**先改快照与交接文档，再改两侧代码**，
而不是我这边先跑起来让它去兼容。
