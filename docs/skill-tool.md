# `skill` 工具：先别写代码（2026-11-03）

## 语料里的真实形状

从 183 个真实会话里抠出的 4 条调用，参数只有一件事：

```json
{"name": "hindsight-coding-agent"}
{"name": "ego-browser"}
```

也就是说：**按名字取一份操作说明**。没有别的字段。

## 为什么这轮不做

我们自己的 home 下**找不到任何 skills 目录**：

```
find "D:/DeepSeek Harness/home" -maxdepth 3 -type d -name skills   → 无
find "D:/DeepSeek Harness/home" -maxdepth 5 -name SKILL.md        → 无
```

而当前实例的 skill 目录是从 DSH 的插件系统来的（会话开头的 catalog 里那一串）。
**在不知道真实存储位置的情况下实现 `skill`，等于自己发明一个格式**，
然后所有真实 skill 都读不到——那比不做更糟：它会"成功返回"，但内容是空的。

## 要做的时候，这样设计（已验证的部分先定死）

1. 目录由接线注入：`skill.Module(dir)`，不自己猜路径
2. `<dir>/<name>/SKILL.md` 为内容；找不到时**列出目录里有哪些名字**，
   而不是只回一句"没有"——模型下一句就能重试对
3. 内容有界（例如 32 KB），超了截断并说明截断位置
4. `Caps` 全 false：只读自己的技能目录，不算写盘

## 什么时候重新打开

- 能确认 DSH 的 skill 存储位置（读它的插件目录或配置）
- 或者我们自己开始产出 skill（那时目录是我们定的，格式自然一致）

## 记一笔

这一轮的价值是**把"能做的"和"该做的"分开了**。
`skill` 排在缺口表上（11 次），但次数少、语义依赖一个我们还没搞清的存储约定。
先记清楚，比先写一个读不到东西的实现强。
